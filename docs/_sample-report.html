01실습 개요

Day 2에서 구축한 근거 기반 답변 API에 도구 호출을 결합해 상담 에이전트를 구현했다. 규정 질의는 RAG로, 주문 조회는 도구로 처리하며, 환불·교환처럼 되돌리기 어려운 행동은 접수 단계에서 중단하고 담당자 승인을 거치도록 했다.

구현의 초점은 기능 추가가 아니라 제약을 프롬프트에서 코드로 옮기는 것에 두었다. 타인의 주문이 조회되지 않는 근거가 "모델에게 거절하도록 지시했기 때문"이라면 검증 실패이고, "질의문에 소유자 조건이 포함되어 있기 때문"이어야 통과로 판정했다. 이 기준의 차이가 본 실습에서 발견한 결함 대부분의 원인이었다.

Advisor 파이프라인

공통으로 해야 할 일(감사 · 차단 · 기억 · 근거 검색 · 계측)을 서비스에서 빼내 Advisor로 모았다. 서비스는 "누가 무엇을 물었나"만 알고, "무엇을 항상 해야 하나"는 설정이 정한다.

요청 →  Audit(0) → Safety(100) → Memory(200) → QA(300) → TokenMeter(900) → 모델
응답 ←  Audit(0) ← Safety(100) ← Memory(200) ← QA(300) ← TokenMeter(900) ←
orderAdvisor그 자리인 이유
0AuditAdvisor차단되든 실패하든 기록은 남아야 하므로 가장 바깥에 배치
100SafetyAdvisor메모리보다 앞에 배치. 뒤로 밀면 차단된 문장이 이미 저장된 뒤가 됨
200MessageChatMemoryAdvisor대명사("그거")를 풀려면 앞 턴이 프롬프트에 들어와야 함
300QuestionAnswerAdvisor근거 검색은 기억을 반영한 질문으로 수행해야 정확함
900TokenMeterAdvisor모델을 가장 가까이 감싸 검색 시간이 모델 지연에 섞이지 않게 함

order를 전부 명시한 이유

다섯 Advisor의 order를 하나도 빠짐없이 적어 두었다. MessageChatMemoryAdvisor는 order를 지정하지 않으면 Advisor.DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER(-2147483448)를 사용하는데, 이 값은 Safety(100)보다 훨씬 앞서므로 메모리가 차단보다 바깥에 놓이게 된다.

순서가 곧 정책인 만큼 기본값에 맡기지 않고 의도한 값을 직접 적는 편이 안전하다고 판단했다. 이 판단에 이르게 된 경위는 09장에 정리했다.

03도구와 권한 격리

도구는 두 종류다. 주문 조회(getOrder)와 접수(requestRefund · requestExchange). 두 도구 모두 사용자 ID를 파라미터로 받지 않는다는 점이 공통된다.

public OrderView getOrder(@ToolParam(...) String orderId, ToolContext context) {
    String userId = ToolUser.of(context);              ① 모델이 못 건드리는 경로
    return orders.findByIdAndOwnerId(orderId, userId)  ③ 권한이 쿼리 안에
            .map(OrderView::from)
            .orElseThrow(() -> new IllegalArgumentException("주문을 찾을 수 없습니다."));
}
.toolContext(Map.of(ToolUser.KEY, principal.getName()))   ② 출처는 인증된 세션

세 겹이 한 메서드에 겹쳐 있다. 그리고 요청 DTO인 ChatRequest에 userId 필드가 없다는 점이 이 설계에서 가장 중요하다 — 이 필드가 있으면 사용자가 자기 신원을 주장할 수 있게 되어 방어 한 겹이 통째로 사라지기 때문이다.

왜 403이 아니라 "찾을 수 없습니다"인가

없는 주문과 남의 주문을 구분해 알려 주면 그 구분 자체가 정보가 된다. 403이 돌아오면 "그 주문은 존재한다"를 알려 준 셈이다. 실제로 99999(타인 소유)와 00000(존재하지 않음)의 응답이 동일하다.

04승인 게이트

환불·교환은 도구가 접수만 한다. 티켓은 PENDING 상태로만 생성되고, 승인으로 가는 경로는 Lab3TicketService에만 있다. 그리고 이 클래스에는 @Tool이 하나도 없다. 모델의 도구 목록에 아예 존재하지 않으므로, 아무리 그럴듯하게 요청해도 승인을 시킬 방법이 없다.

@RestController @RequestMapping("/lab3/admin")
@PreAuthorize("hasRole('ADMIN')")            역할 검사가 한 겹 더
public class Lab3AdminController { ... }

방어가 두 군데에 있다 — 시큐리티 설정의 URL 규칙과 메서드의 @PreAuthorize. URL 규칙만 두면 나중에 경로를 바꿀 때 조용히 열릴 수 있고, 애너테이션만 두면 설정을 훑어보는 것만으로는 보호 여부를 알기 어렵다.

3턴이 이 시나리오의 하이라이트

"그럼 그거 반품 돼요?" 한 문장을 처리하려면 셋이 동시에 살아 있어야 한다 — 메모리가 "그거"를 2턴의 주문 12345로 해석하고, RAG가 1턴에서 확인한 반품 규정을 근거로 삼으며, 도구가 해당 주문의 실제 상태를 확인해야 한다. 하나라도 빠지면 답이 어긋난다.

⑤번 줄을 눈여겨볼 것

판정 근거가 "거절하도록 프롬프트를 썼다"가 아니라 "그런 도구를 만들지 않았다"라는 점이다. 정규식은 띄어쓰기나 자모 분리로 우회할 수 있지만, 존재하지 않는 도구는 우회할 방법이 없다. 할 수 없게 만드는 것이 가장 강한 방어라고 생각한다.

⑧에서 발견한 것 — 방어선은 우리 코드 밖에도 있다

Swagger의 GET으로 3,000자를 입력하자 우리 거절 문구가 아니라 Tomcat의 400 에러가 반환되었다. 한글은 URL 인코딩하면 한 글자가 9바이트가 되어 약 900자부터 요청 헤더 상한(8KB)을 넘는다.

09구현 과정에서 확인한 문제와 개선

구현과 검증을 진행하며 여섯 가지를 확인해 수정했다. 모두 응답만 보아서는 정상으로 보이는 유형이었다는 공통점이 있어, 각각을 어떤 의도로 어떻게 고쳤는지 함께 남긴다.

1 — Advisor의 order를 명시하지 않은 상태

인젝션을 차단하는 과정에서 conversationId cannot be null로 500이 발생했다. 확인해 보니 MessageChatMemoryAdvisor를 order 없이 생성한 탓에 기본값 -2147483448이 적용되어, 메모리가 차단보다 바깥에 놓여 있었다. 의도한 배치는 차단(100) → 메모리(200)였으므로 완료 기준 6번의 조건과 어긋난 상태였다.

응답은 어느 배치에서든 동일하게 "거절"이라, 500이 발생하지 않았다면 끝까지 확인하지 못했을 문제였다. 이에 다섯 Advisor의 order를 모두 명시하고, 같은 실수가 반복되지 않도록 순서를 검사하는 테스트를 추가했다. SafetyAdvisor가 차단 응답을 만들 때 요청 컨텍스트를 이어받도록 한 것도 이때 함께 손봤다.

2 — traceId가 한 턴을 못 따라갔다

도구가 있으면 모델을 두 번 호출하는데, 두 번째 호출이 새 컨텍스트로 들어오면서 traceId가 갈라졌다. 답변 자체는 정확해서 로그를 들여다보아야만 드러나는 문제였다. traceId를 요청 단위를 아는 곳(서비스)에서 생성해 넘기도록 수정했다.

3 — 대화 ID 규칙의 기본값이 흩어져 있었다

POST는 default, GET과 이력 조회는 s1을 기본값으로 쓰고 있었다. sessionId 없이 POST로 대화한 뒤 이력을 조회하면 다른 대화를 보게 된다. 강의안이 주의를 준 "남의 대화가 섞이는 사고"의 가장 가벼운 형태에 해당한다. 규칙 자체는 한 곳에 모아 두었지만 기본값이 밖으로 새어 나가 있었다.

4 — 모델이 담당자의 권한을 가로챘다

강의안의 5턴 시나리오를 그대로 실행했을 때 환불이 접수되지 않았다.

4턴) 환불로 접수해 주세요
     "환불을 접수해 드리겠습니다. 환불 사유를 말씀해 주시면 진행하겠습니다."
5턴) 색상이 마음에 안 들어서요
     "죄송하지만, 색상 변경은 교환으로 처리할 수 있으며, 환불 접수는 불가능합니다."
     toolCalls: []                              도구가 안 불렸다

"교환 말고 환불로 접수해 주세요"라고 명시해도 계속 거절했다. 원인은 세 가지가 겹쳐 있었다.

(a) 추론 오류. RAG가 "색상 교환 1회 무상" 조항을 물어다 주자 모델이 "색상 = 교환 대상 → 환불 불가"로 판단했다. 그런데 규정을 다시 읽어 보면 그런 내용은 없다 — 단순 변심 반품은 7일 이내 가능하고, 교환은 선택지를 하나 더 제공하는 것이지 반품을 배제하는 조항이 아니다. 더 구체적으로 들리는 조항이 일반 조항을 덮어쓴 사례로 볼 수 있다.

더 나쁜 것은 이것이 승인 게이트를 무력화한다는 점이다. 모델이 접수 단계에서 미리 거절해 버리면 담당자는 그런 요청이 있었다는 사실조차 알 수 없다. "도구는 접수만, 판단은 사람이"라는 원칙이 모델의 자체 판단으로 무너지는 셈이다.

(b) 안내는 하는데 처리할 도구가 없었다. 교환을 안내해 놓고 교환 접수 도구는 만들지 않았다. 사용자가 "그럼 교환으로"라고 답하면 더 진행할 방법이 없다.

(c) 도구 설명이 과하게 조심스러웠다. "불분명하면 되묻는다"를 넣어 두었더니, 주문번호가 이미 대화에 등장했는데도 계속 되물었다.

먼저 시도했던 방식과 그것을 바꾼 이유

시스템 프롬프트에 "환불을 요청하면 무조건 접수해 준다"를 넣었다. 도구는 호출되기 시작했지만 모델은 여전히 "색상 = 교환"이라는 이해를 유지한 채 접수만 수행했고, 사용자가 선택할 기회는 마련되지 않았다. 증상만 보고 프롬프트부터 손대면 원인은 그대로 남는다는 것을 확인하고, 아래와 같이 접근을 바꾸었다.

제대로 고친 곳은 세 군데였다. 문서에 "색상·사이즈도 단순 변심에 해당하며 반품과 교환 중 선택할 수 있다"를 명시하고(Day 2의 교훈 — 프롬프트보다 문서가 먼저다), 프롬프트에 "선택지를 임의로 배제하지 않는다"를 넣고, 교환 접수 도구를 추가했다.

중복 방지 조건도 (주문, 종류, PENDING)으로 변경했다. 종류를 보지 않으면 "반품을 접수했다가 교환으로 바꾸고 싶다"는 정상 요청까지 막히기 때문이다.

5 — "막혔다"와 "코드가 막았다"는 다르다

권한 실습에서 차단은 되는데 toolCalls가 비어 있었다. 본인 주문 조회가 성공하면 모델이 "이 사용자의 주문은 99999"라고 받아들여, 다른 번호에는 조회를 건너뛰고 스스로 거절한 것이다. 소유 여부는 모델이 알 수 없는 정보인데도 알고 있는 것처럼 판단한 셈이다.

보안이 뚫린 것은 아니다. 다만 감사 로그에 시도가 남지 않는다. 타인의 주문을 조회하려는 시도가 있었는데 흔적이 없으면, 보안 모니터링에 사각지대가 생긴다.

도구 설명과 프롬프트를 수정했지만 효과는 부분적이었다 — 모델에게 도구 호출을 강제할 수는 없기 때문이다. 그래서 실습 절차 쪽을 바꾸었다. 권한 테스트는 케이스마다 세션을 분리하고, 남은 한계는 한계로 기록해 두었다.

6 — 방어선은 우리 코드 밖에도 있다

08장에 적은 대로, 초장문 GET은 Tomcat이 먼저 거절한다. 공격은 더 앞 단계에서 막혔지만, 사용자가 받는 것은 우리 메시지가 아니며(내부 스택트레이스가 노출된다) 감사 로그에도 남지 않는다. "막혔으니 됐다"가 아니라 "어디서 막혔고 그것이 기록에 남는가"까지가 관찰의 범위라고 본다.

10Day 2 코드 재정비

Day 3의 도구와 Advisor를 얹으려면 Day 2 구조에서 두 가지를 먼저 바꿔야 했다. 둘 다 Day 2까지는 문제가 되지 않던 것들이다.

첫째는 ChatClient를 서비스가 직접 만들고 있었다는 점이다. Day 2에서는 서비스마다 builder.build()로 즉석 생성해도 충분했지만, Day 3의 정책은 대부분 Advisor에 들어간다. Advisor를 걸 자리가 없으면 감사도 차단도 계측도 붙일 수 없다. 그래서 ChatClient를 설정의 빈으로 옮기고 시스템 프롬프트와 옵션도 함께 모았다. lab3의 assistantChatClient가 같은 모양을 따르므로, 두 실습의 클라이언트 정의를 나란히 놓고 비교할 수 있게 되었다.

둘째는 예외가 그대로 500으로 나가고 있었다는 점이다. Day 3에서는 도구 실패와 권한 거절이 예외로 올라오는데, 이것들이 한 덩어리로 500이 되면 사용자도 우리도 원인을 구분할 수 없다. 공용 ApiExceptionHandler를 두어 404·403·503을 갈라 내보내고, 응답에는 내부 사정 대신 traceId만 담도록 했다. 이 traceId가 07장의 로그 추적과 이어진다.

나머지 변경 — 패키지명과 프로젝트 식별자를 practice3로 맞추고, Security·AspectJ·H2 같은 의존성을 추가한 것 — 은 Day 3를 시작하기 위한 준비 작업이라 따로 적지 않는다.

반대로 손대지 않기로 한 것도 있다. Lab2Settings의 가변 상태는 실험 파라미터를 재시작 없이 바꾸려는 목적이 분명하고, SimpleVectorStore 역시 Day 2 범위에서 의도한 선택이었다. 판단 근거가 코드에 남아 있는 부분은 그대로 두는 편이 낫다고 보았다.
