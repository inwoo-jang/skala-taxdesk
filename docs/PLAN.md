> 교재 13장(p.308~323) 종합실습. 큰 주제 **HelpDesk AI**(고객 문의를 RAG·Tool 로 응대하는 AI)를 유지하되,
> practice1~3이 다루지 않은 문제 하나에 집중한다 — **"저 종합과세 대상인가요? 세금 얼마 나와요?"**

- 루트 패키지: `com.inwoo.taxdesk`

## 0. 누구를 위한 서비스인가 — 이걸 먼저 정한 이유

같은 기능도 **누가 운영하느냐**에 따라 설계가 달라진다. 특히 이 실습에서는
"거절"과 "면책"이 핵심 설계 요소라서, 서비스 주체를 정하지 않으면 그 둘의 근거가 서지 않는다.

**주체: 가상의 증권사 `SKALA증권`. 사용자: 자사 계좌를 보유한 개인 고객.**
**실존 모델: 증권사들이 연말에 보내는 "금융소득 종합과세 대상 예상 안내" 서비스.**

국세청(홈택스)이 아니라 증권사를 고른 이유는 셋이다.

| 설계 요소 | 국세청이라면 | 증권사라면 |
|---|---|---|
| `OUT_OF_SCOPE` 즉시 거절 | **성립하지 않는다.** 양도세도 국세청 소관이다. 거절하면 설계가 아니라 버그로 읽힌다 | **성립한다.** 금융소득 외에는 업무 범위도 데이터도 없다 |
| "참고용, 최종 판단은 세무 전문가" 고정 문구 | 어색하다. 국세청이 곧 과세권자다 | **필연이다.** 세무사법상 증권사는 세무대리를 할 수 없다 |
| `otherIncome`(근로소득 등)을 고객이 입력 | 이상하다. "너희가 이미 알잖아" | **자연스럽다.** 우리는 자사 계좌만 안다 |
| 세무사 상담 예약 게이트 | 명분이 약하다 | 실존한다. VIP 제휴 세무사 상담 |

핵심은 첫 줄이다. **업무 범위가 좁은 주체를 골라야 "거절"이 정직한 답이 된다.**
그리고 "우리는 우리 계좌만 안다"는 한계를 숨기지 않고 UI 와 응답에 명시하는 것 자체가 이 실습의 설계다.

> 면책 근거: 세무사법 §2 — 세무대리는 세무사·세무법인만 할 수 있다.
> 따라서 이 서비스가 낼 수 있는 것은 **"예상 안내"**이지 **"신고 대리"**가 아니다.
> 이 법적 제약이 시스템 프롬프트의 고정 문구와 승인 게이트를 동시에 정당화한다.

## 1. 왜 이 문제인가

practice1~3과 겹치지 않으려면 **부품**이 아니라 **부품이 협력하는 방식**이 달라야 한다.
practice3의 "주문 조회"는 사실 DB SELECT 라 Tool 이 장식에 가깝다. 여기는 다르다.

| | 문서만 있으면 | 계산만 있으면 |
|---|---|---|
| "배당소득 세율이 뭔가요?" | 답 가능 | 답 불가 |
| "이자 1,200 배당 900이면 세금 얼마?" | 답 불가 | 답 가능 |
| **"저 종합과세 대상인가요?"** | **답 불가** | **답 불가** |

세 번째 줄이 이 실습의 존재 이유다. 법령에서 **기준(2,000만원)** 의 근거를 찾아오고,
그 기준으로 **계산**하고, 근거와 계산식을 **둘 다** 출처로 제시해야 답이 된다.

핵심 주장 한 줄: **"LLM에게 산수를 시키지 않는다. 대신 근거와 계산을 둘 다 증명한다."**

## 2. 시나리오

| 누가 | 무엇을 묻고 | 무엇이 필요한가 | 부품 |
|---|---|---|---|
| 고객 | "금융소득 2천만원 넘으면 어떻게 되나요?" | 법령 근거 + 조문 출처 | RAG |
| 고객 | "제 2026년 이자·배당 얼마죠?" | **자사 계좌** 내역 조회 | Tool |
| 고객 | "그럼 저 종합과세 대상이에요?" | 근거 + 판정 계산 | RAG + Tool |
| 고객 | "세금은 얼마나 나와요?" | 비교과세 산출 (앞 턴 금액 + 근로소득 입력) | Tool + Memory |
| 고객 | "세금 줄일 방법 없나요?" | 절세상품 안내 + 자격확인 신청 | RAG + Tool + 승인 게이트 |
| 고객 | "이 주식 오를까요?" | **투자자문 거절** (자본시장법) | 설계된 거절 |
| 고객 | "타사 계좌 배당도 합쳐줘요" | **한계 고지** 후 수동 입력 유도 | 설계된 거절 |
| 운영자 | "어제 토큰이 왜 늘었지?" | 토큰 · 지연 · 도구 호출 지표 | 관찰 |

여섯 번째 줄이 증권사를 고른 보람이다. 못 하는 것을 못 한다고 말하고, 대안을 주는 것도 응대다.

## 3. 스코프 — 자르는 것이 설계다

### 다룬다
- **자사 계좌의 이자소득 · 배당소득**만 조회한다
- **비과세 · 분리과세 · 종합과세를 구분**한다 (`TaxTreatment`) — 세 갈래는 답변 문구가 다르다

| 과세방식 | 예 | 답변 | 근거 |
|---|---|---|---|
| 비과세 | 비과세종합저축(원금 5천만), ISA 한도 이내 | "세금 자체가 없습니다" | 조특법 §88의2 · §91의18 |
| 분리과세 | ISA 한도 초과분 **9%**, 고배당기업 특례배당 | "별도 세율로 **과세가 끝났습니다**" | 조특법 §91의18 · §104의27 |
| 종합과세 | 그 외 이자·배당 | 2천만원 초과 판정 대상 | 소득세법 §14③6호 |

> ISA 비과세 한도는 **일반 200만원 / 서민형 400만원** (조특법 §91의18②). 확대 개정 없음.
> 비과세종합저축은 **2028-12-31까지 가입분** — 일몰이 살아 있다.
- 타사 금융소득과 **그 외 종합소득**(사업·근로·연금·기타)은 **고객이 입력하는 숫자**로만 받는다
  (`externalAmount` · `otherIncome` · `prepaidTax`)
  → `otherIncome` 은 "근로소득"이 아니라 **"이자·배당을 제외한 종합소득금액 합계"** 다 (§14②)
- 2,000만원 초과 판정 · 비교과세 · Gross-up · 배당세액공제 · 지방소득세

### 다루지 않는다 (명시적 제외 · `OUT_OF_SCOPE` 로 거절)

거절을 **세 갈래**로 나눈다. 이 구분의 근거는 소득세법 §14 다 — 종합소득에 합산되는가 아닌가로 갈린다.

| 갈래 | 대상 | 응답 | 근거 |
|---|---|---|---|
| **합산 가능** (권한 밖) | 사업 · 근로 · 연금 · 기타 · 부동산임대소득 | "저희가 **계산해 드릴 수는 없지만**, 이미 아시는 소득금액을 알려주시면 합산해 판정·계산해 드립니다" | §14② — 종합소득금액 = 이자+배당+**사업+근로+연금+기타** |
| **합산 가능** (권한 밖) | 타사 금융소득 | "조회 권한이 없습니다. 금액을 알려주시면 합산해 드립니다" | 자사 계좌만 조회 가능 |
| **합산 불가** (진짜 범위 밖) | **양도소득 · 퇴직소득** | "안내드리지 않습니다" (대안 없음) | §14① — **분류과세**라 종합소득과세표준에 애초에 합산되지 않는다 |

마지막 줄이 중요하다. 양도·퇴직을 거절하는 것은 "우리가 몰라서"가 아니라
**법적으로 합산 대상이 아니어서**다. 거절에 조문 근거가 붙는다.

- 타사 계좌 실시간 조회 → **"조회 권한이 없습니다. 금액을 알려주시면 합산해 드립니다"**
- 인적공제 상세 (소득공제 합계를 고객이 입력)
- 실제 신고 대리 → 세무사법 §2 상 불가. 절세상품 **자격확인 신청**까지만
- **투자자문 · 종목 전망 · 매매 타이밍** → 자본시장법상 투자자문은 등록한 자만 할 수 있다.
  세무 창구에서 종목 전망을 말하면 그건 안내가 아니라 **무등록 투자권유**다
- **개인투자용 국채**(만기보유 시 2억원 한도 분리과세) 등 상품별 특례 → **다루지 않는다.**
  상품이 늘 때마다 계산 분기가 늘어 실습의 초점이 흐려진다. 05번 문서에 "안내 범위 밖"으로 명시
- 세액 정확도 보증 → **"예상 안내이며 최종 판단은 세무 전문가"** 고정 문구

### 계산 규칙 명세 (실습용 단순화 · 2026 귀속 기준)

```
금융소득 = 이자소득 + 배당소득(비과세·분리과세 상품 제외)
         = 자사 계좌 합계 + 고객이 입력한 타사 금액

[0] 먼저 판정한다 — 분리과세인가 종합과세인가        (소득세법 §14③6호 · §62)
    이 순서는 우리가 정한 게 아니라 법 조문의 구조다. §62 는
    "기준금액을 초과하지 아니하는 경우에는 제2호(분리과세)의 금액으로 한다"고 못 박는다.

[1] 금융소득 ≤ 2,000만원  →  분리과세 종결 (원천징수 14%로 끝, 종합신고 불필요)
                              ※ 여기서 끝난다. 세액 계산 도구를 부르지 않는다.
[2] 금융소득 >  2,000만원  →  종합과세, 아래 비교과세

  ── 배당가산(Gross-up) 4단계 ── 한 줄로 뭉개면 반드시 틀린다
  ① eligibleDividend  = Gross-up 가능 배당 (내국법인·법인세 과세된 재원)
  ② targetAmount      = min(①, 금융소득 - 2,000만)    ← 배당 전액이 아니다 (§56④)
  ③ 배당가산액        = ② × 10%                        (소득세법 §17③ "100분의 10")
  ④ 배당세액공제      = ③ 상당액 (법정 한도 적용)      (소득세법 §56)
  종합소득금액  = (금융소득 - 2,000만) + 배당가산액 + otherIncome
                  └ otherIncome = 사업+근로+연금+기타 소득금액 합계 (고객 제공 · §14②)
  과세표준      = 종합소득금액 - deduction

  ① 종합과세 산출세액 = 누진세율(과세표준) + 2,000만 × 14% - 배당세액공제(④)
  ② 분리과세 산출세액 = 금융소득 × 14% + 누진세율(otherIncome - deduction)

  결정세액 = max(①, ②)          ← 비교과세 (소득세법 §15 2호 "비교하여 큰 금액")
  지방소득세 = 결정세액 × 10%     (별도)

[3] 기납부세액과 실제 부담액  ← 고객이 진짜 궁금해하는 숫자

  기납부세액 = 자사 이자·배당 원천징수세액   (우리가 안다 · AccountIncome.withheldTax)
             + 타사 금융소득 원천징수세액    (고객 입력)
             + 근로소득 등 결정세액          (고객 입력 · 연말정산 결과)

  납부할세액 = 결정세액 - 기납부세액
             ├ 양수 → 추가 납부
             └ 음수 → 환급          ← 실제로 흔하다. 이걸 못 보여주면 서비스가 반쪽이다
```

> **왜 [3]이 필요한가.** 결정세액만 말하면 "세금 2,000만원 나옵니다"가 되는데,
> 이자·배당은 지급 시점에 이미 14% 원천징수됐고 근로소득은 연말정산으로 이미 냈다.
> 실제로 더 낼 돈은 300만원일 수도 있고, **환급일 수도 있다.**
> 결정세액에서 멈추면 고객을 불필요하게 놀라게 하는 서비스가 된다.

> **주의 — 이중차감.** ②의 산출세액에는 금융소득 14%가 이미 들어 있다.
> 기납부세액 차감은 반드시 `max(①,②)` **이후에** 한 번만 한다.

### 실습 단순화 — 하지 않는 것을 명시한다

정확도를 보증하지 않는 대신 **어디까지가 단순화인지**를 답변과 문서에 밝힌다.
말없이 근사하는 것이 이 프로젝트에서 가장 나쁜 실패다.

| 항목 | 실제 세법 | 이 실습 | 답변에 표시 |
|---|---|---|---|
| **배당세액공제 한도** | §56 + 시행령의 법정 한도 계산 | 한도 미적용 (가산액 전액 공제) | "한도 계산은 생략된 예상치" |
| **외국납부세액공제** | §57. 해외배당 원천지국 납부세액 | **미구현** | "해외 배당이 있으면 별도 공제 대상일 수 있습니다" |
| **고배당기업 특례** | 조특법 §104의27 (아래) | 판정 불가 · **안내만** | 세무사 상담 유도 |
| **기장세액공제** | §56의2. 사업소득 전용 | 범위 밖 | "사업소득 관련 공제는 안내 범위 밖" |
| Gross-up 세부 제외항목 | §17③ 각 호 (의제배당·자본준비금 감액배당 등) | 내국/외국 배당 구분만 | — |

> 특히 **외국납부세액공제**를 빠뜨리면 안 되는 이유: 해외배당은 Gross-up 대상이 *아니지만*
> 외국납부세액공제 대상은 *될 수 있다.* 둘을 혼동하면 "해외배당은 아무 혜택이 없다"는
> 틀린 안내가 나간다. 계산은 못 해도 **존재는 알려야 한다.**

### 2026 신설 — 고배당기업 배당소득 분리과세 `조특법 §104의27`

**[본조신설 2025. 12. 23.]** — 2026 귀속을 기준으로 잡은 덕에 들어온 조항이다.

```
요건 (모두 충족한 내국법인 = "고배당기업")
  1. 주권상장법인 (코넥스 제외, 투자회사 등 제외)
  2. 직전 사업연도 배당이 2024 사업연도보다 감소하지 않았을 것
  3. 가. 직전 사업연도 배당성향 40% 이상, 또는
     나. 배당성향 25% 이상 + 이익배당금액이 전전 사업연도 대비 10% 이상 증가

효과: 특례배당소득을 종합소득과세표준에 합산하지 않는다 (§14② 적용 배제)
      분리과세 세율 2,000만 이하 14% / ~3억 20% / ~50억 25% / 50억 초과 30%
      ※ 적용 기한: 2028 사업연도까지
```

**스코프 결정: 판정하지 않는다. 안내만 한다.** 이유 셋.

1. **요건 판정에 기업 재무데이터가 필요하다** — 배당성향·전년 대비 증감은 우리가 가진 계좌
   내역으로 알 수 없다. 고배당기업 여부는 **해당 기업이 공시**한다(§104의27④)
2. **거주자가 직접 "합산배제 신청"을 해야 한다**(§104의27③). 우리가 대신 할 수 없다 —
   세무사법 §2 제약과 정확히 같은 성격이다
3. 대통령령 위임 사항이 많다 ("대통령령으로 정하는 금액")

대신 이렇게 응대한다 — **못 하는 것을 못 한다고 말하고 대안을 주는** 이 프로젝트의 기존 패턴 그대로다.

> "고객님 배당 중 고배당기업 특례 대상이 있다면 합산배제 신청으로 세부담이 줄 수 있습니다.
>  다만 대상 여부는 **해당 기업 공시**로 확인하셔야 하고 **신청은 본인이** 하셔야 합니다.
>  제휴 세무사 상담을 예약해 드릴까요?"  → **ACTION 라우트로 연결**

보고서 관점에서 이 조항의 값어치는 따로 있다.
**세법 개정이 실제로 일어난 지점**이라, "세법 개정 = 코드 배포가 아니라 설정·문서 교체"라는
이 프로젝트의 주장을 **가정이 아니라 실물로** 보여준다.

누진세율표 (과세표준 / 세율 / 누진공제):

| 과세표준 | 세율 | 누진공제 |
|---|---|---|
| 1,400만 이하 | 6% | 0 |
| ~5,000만 | 15% | 126만 |
| ~8,800만 | 24% | 576만 |
| ~1.5억 | 35% | 1,544만 |
| ~3억 | 38% | 1,994만 |
| ~5억 | 40% | 2,594만 |
| ~10억 | 42% | 3,594만 |
| 10억 초과 | 45% | 6,594만 |

> 세율표는 **코드 상수가 아니라 설정(`taxdesk.brackets`)** 에 둔다. 세법 개정 = 설정 교체.
> RAG 문서에도 같은 표를 넣어 "문서가 말하는 값"과 "코드가 쓰는 값"의 일치를 골든셋으로 검증한다.

## 4. 아키텍처

```
고객 / 운영자
   │
   ├─ static/index.html  (SSE 채팅 · 출처 · 계산 전개 시각화)
   └─ swagger-ui.html    (계정 전환 · 소유자 격리 시연)
   │
   ▼
web/        ChatController(REST · SSE) · AdminController(인제스트 · 승인) · SecurityConfig
   │
   ▼
chat/       TaxDeskService  ── QueryRouter(4분기) ── 출처·계산 병합
   │
   ▼
AI 계층     ChatClient
              └ Advisor 체인  Audit(0) → Safety(100) → Memory(200) → QA(300) → TokenMeter(900)
   │
   ├── 근거   rag/      VectorStore ← IngestService (청크 + 조문 메타데이터)
   ├── 행동   tools/    AccountIncomeTools · TaxCalcTools · ConsultationTools
   ├── 데이터 repository/ AccountIncomeRepository · ConsultationRepository (계좌 소유자 격리)
   └── 운영   advisor/  AuditAdvisor · TokenMeterAdvisor · 폴백 ChatClient
```

### 라우터 — 이 실습의 고유 설계 포인트

```
질문 → QueryRouter
 ├ REGULATION   규정 질문        → RAG only            "배당소득세율이 뭔가요?"
 ├ CALCULATION  금액 계산        → Tool only           "이자 1200 배당 900이면?"
 ├ HYBRID       판정 필요        → RAG + Tool          "저 종합과세 대상인가요?"
 ├ ACTION       예약 · 신청      → Tool + 승인 게이트   "세무사 상담 예약이요"
 └ OUT_OF_SCOPE 범위 밖          → 즉시 거절 (모델 호출 X)  "양도세는 얼마예요?"
```

- 라우팅은 **모델 1회 분류 호출**(저비용 모델·structured output). 규칙 기반 폴백 병행.
- OUT_OF_SCOPE 는 주 모델을 아예 안 부른다 → 비용·안전 동시 방어
- 거절은 두 종류다. **업무 범위 밖**(양도세)과 **권한 밖**(타사 계좌). 후자는 대안을 함께 준다.
- HYBRID 는 RAG 근거의 **기준값을 파싱해 Tool 입력으로 넘기지 않는다**. 기준은 설정에 있고,
  RAG 는 그 기준의 **근거 문서**를 제시할 뿐 — 이 분리를 보고서에 명시한다.

## 6. Phase 1~8 상세

### Phase 1 — 뼈대와 Advisor 조립 `config/`
- **목표**: ChatClient 1개 + Advisor 체인 순서 확정, 모든 임계값 설정 외부화
- **산출물**: `AiConfig`, `TaxDeskProperties`, `application.properties`
- **체인**: `Audit(0) → Safety(100) → Memory(200) → QA(300) → TokenMeter(900)`
- **시스템 프롬프트 고정 규칙**
  - 세법 질문은 [근거] 안에서만 답하고 없으면 "확인되지 않습니다"
  - 답변 끝에 `[출처: 파일명 · 조문]`
  - **금액·세액은 반드시 도구 결과만 사용. 직접 계산 금지**
  - 조회 범위는 **SKALA증권 계좌로 한정**. 타사 금액은 고객에게 물어본다
  - 답변 말미 "예상 안내이며 최종 판단은 세무 전문가" 고정
- **검증**: 앱 기동 + `/actuator/health` 200

### Phase 2 — RAG 인제스트 `rag/`
- **목표**: 세법 요약 문서 → 청크 → 벡터, **조문 단위 메타데이터** 부여
- **practice3와 다른 점**: 청크 메타에 `article`(조문), `effectiveYear`(귀속연도) 추가 →
  출처가 "파일명"이 아니라 **"소득세법 §14③ (2026 귀속)"** 으로 나온다
- **청크 전략**: 조문 경계 우선 분할(헤딩 기준), 400자 목표 / 최소 50자
- **검증**: 인제스트 후 청크 수 · 조문 메타 누락 0건

### Phase 3 — 라우터와 QA 흐름 `chat/`
- **목표**: 4분기 라우팅 + REGULATION 경로 완성 (출처 강제)
- **검증**: 규정 질문 10건 전부 출처 포함 / OUT_OF_SCOPE 질문에 주 모델 호출 0회

### Phase 4 — 도구와 데이터 `tools/` `repository/` `domain/`
- **목표**: CALCULATION · HYBRID 경로 완성
- **도구 명세**

| 도구 | 입력 | 출력 | 비고 |
|---|---|---|---|
| `lookupMyAccountIncome` | year | 이자 · 배당 · 원천징수세액 · 상품별 내역 | **계좌 소유자 격리** (`findByOwnerIdAndYear`) · 자사 한정 |
| `classifyTaxation` | interest, dividend, externalAmount | 분리/종합 판정 + 초과액 + 적용 기준 | 기준값은 설정에서 |
| `calculateTax` | 금융소득, otherIncome, deduction, **prepaidTax** | 비교과세 ①② 전개 + 결정세액 + 지방세 + **납부할세액/환급액** | **계산 근거 문자열 동봉** |
| `estimateDueDate` | year | 신고·납부 기한, 가산세 | 기한 계산 |

- **핵심**: `calculateTax` 는 숫자만 반환하지 않고 **`steps[]` (계산 전개 과정)** 을 함께 반환한다.
  모델은 이걸 그대로 인용만 한다 → hallucination 지점 제거
- **자사 한정의 강제**: `lookupMyAccountIncome` 에는 "타사"를 넣을 파라미터가 **아예 없다.**
  프롬프트로 "타사는 조회하지 마"라고 부탁하는 대신 부를 수 없게 만든다.
- **검증**: 경계값(1,999만 / 2,000만 / 2,001만) 단위 테스트, 비교과세 ①<② 케이스 포함

### Phase 5 — 메모리와 멀티턴 `chat/`
- **목표**: "그럼 저는요?" / "근로소득 5천 있으면?" 이 동작
- **주의**: Safety(100)를 Memory(200) **앞**에 둬야 차단된 문장이 기억에 안 남는다
  → `safety-order` 설정으로 100/250 을 바꿔가며 시연
- **검증**: 3턴 대화 시나리오 5종, 다른 고객 세션 간 정보 누출 0건

### Phase 6 — API · 스트리밍 · 화면 `web/` `static/`
- **목표**: REST + **SSE 스트리밍** + 구조화 응답 + 단일 HTML 채팅 화면
- **`AnswerDto`**
  ```
  { route, answer, citations[{doc, article, score}],
    toolCalls[{name, args, result}], calculation{steps[], total},
    tokens{prompt, completion}, latencyMs, disclaimer }
  ```
- **화면**: `static/index.html` 한 장. 빌드 도구 없는 바닐라 HTML+JS.
  왼쪽에 대화, 오른쪽에 **이번 답변의 출처 · 도구 호출 · 계산 전개**를 펼쳐 보인다.
  "근거와 계산을 둘 다 증명한다"는 주장을 눈으로 보여주는 것이 이 화면의 목적이다.
- **Swagger UI**: 계정을 바꿔가며 같은 질문을 던지는 **소유자 격리 시연**용으로 유지
- **검증**: 첫 토큰 도달 시간(TTFT) 측정, 비스트리밍 P95 5초 이내

### Phase 7 — 보안 · 승인 게이트 · 감사
- **승인 게이트**: `ProductApplicationTools.requestEligibilityCheck()` 는 `PENDING` 까지만.
  결정은 관리자 `POST /admin/applications/{id}/approve` · `/reject`
  → 게이트의 근거가 설계 취향이 아니라 **법**이다: 조특법 §88의2③ "가입대상의 **확인**"
  → **거절이 정상 경로다.** 비과세종합저축 자격은 열거주의라 미해당 고객이 훨씬 많다
- **권한 격리**: 타인 계좌 조회 시도 → **쿼리 레벨 차단**(프롬프트 아님)
- **안전**: 입력 길이 상한, 프롬프트 인젝션 패턴, 주민번호·계좌번호 마스킹(`Masker`)
- **감사**: `AuditAdvisor`(대화) + `ToolAuditAspect`(도구) 두 층
- **검증**: 레드팀 프롬프트 10종 전부 차단, 승인 없이 상태 확정 시 실패

### Phase 8 — 평가 · 관찰 · 복원력 `eval/` `advisor/`
- **골든셋 3종**
  - `regulation` — 출처 정확도 (기대 조문 포함 여부)
  - `calculation` — 세액 정확도 (기대 금액 완전 일치)
  - `safety` — 차단 여부 (업무 범위 밖 · 권한 밖 · 인젝션)
- **지표**: `taxdesk.tokens{type}`, `taxdesk.latency{route}`, `taxdesk.tool.calls{name}`,
  `taxdesk.route{type}`, `taxdesk.fallback.count` → Prometheus
- **폴백**: 주 모델 실패 시 보조 모델 ChatClient 로 재시도
- **검증**: `./gradlew test -Peval`, 장애 주입(잘못된 키) 시 응답 지속
