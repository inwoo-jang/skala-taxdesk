# SKALA증권 세무상담 데스크 — 실습 보고서 초안

2026년 귀속 금융소득(이자·배당)의 종합과세 여부와 예상 세액을 안내하는 상담 시스템입니다.
RAG와 Tool을 함께 쓰되 **역할을 분리한 설계**를 세웠고, 질문 90여 건을 실제로 돌려 검증했습니다.

---

## 1. 결론

**세 가지 주장 중 둘은 증명됐고, 하나는 부분적으로 깨졌습니다.**

| 주장 | 검증 결과 |
|---|---|
| ① 모델에게 산수를 시키지 않는다 | **증명됨** — 계정 5명 전원 세액이 골든셋과 완전 일치 |
| ② 거절은 비용이 들지 않아야 한다 | **대체로 증명됨** — 거절·차단 17건 토큰 0, 1건 누수 |
| ③ 격리는 프롬프트가 아니라 쿼리로 강제한다 | **증명됨** — 단, 기억 계층에서 유출을 발견해 수정 |

가장 중요한 발견은 **실패가 한 방향으로 몰렸다는 점**입니다.
**계산(도구)은 전부 맞았고, 검색·분류(언어)는 자주 틀렸습니다.**
이 분포 자체가 "숫자는 코드에 맡긴다"는 설계를 뒷받침합니다.

동시에 그 설계가 **RAG 경로까지 덮지 못한다**는 한계도 드러났습니다.
도구 경로에는 인용 충실도 검사(답변 금액 ↔ 도구 반환값)가 있지만,
규정 질문에는 대응하는 검증 장치가 없어 **틀린 세율이 출처와 함께 나갔습니다.**

---

## 2. 설계

질문을 먼저 5개 경로로 분류하고, 경로가 부품을 결정합니다.
어떤 부품을 부를지 모델에게 매번 맡기지 않습니다.

| 경로 | 부품 | 예시 |
|---|---|---|
| REGULATION | RAG | 배당소득 세율이 몇 퍼센트인가요? |
| CALCULATION | Tool | 제 이자·배당 얼마인가요? |
| HYBRID | RAG + Tool | 저 종합과세 대상인가요? |
| SIMULATION | Tool(역산) | 얼마까지 더 받아도 되나요? |
| OUT_OF_SCOPE | **없음 (모델 호출 0)** | 이 주식 오를까요? |

핵심은 세 가지입니다.

**분류를 규칙 → 모델 2단으로 둡니다.** 거절해야 할 것은 정규식으로 먼저 잡습니다.
모델을 먼저 부르면 거절 케이스에서도 토큰이 나가고, 그러면 "거절은 공짜"가 성립하지 않습니다.

**도구 호출 순서를 코드가 정합니다.** 조회 → 판정 → (종합과세일 때만) 계산 순서이며,
이는 소득세법 §62의 구조입니다. 분리과세 고객에게 세액을 계산해 보여주는 사고를 막습니다.

**소유자 조건을 쿼리에 박습니다.** 도구 시그니처에 타인 ID를 넣을 자리를 두지 않습니다.
"남의 계좌를 보지 마라"고 부탁할 필요 자체를 없앴습니다.

## 3. 검증 결과

계정 5명 · 질문 90여 건 · 캡처 82장. 주 답변 모델 `gpt-4o`, 라우터·폴백 `gpt-4o-mini`.

| 축 | 결과 |
|---|---|
| 세액 정확도 | **5/5 완전 일치** |
| 소유자 격리 | **5/5** |
| 거절 비용 | **17건 토큰 0** (1건 누수) |
| 라우팅 | 11/12 |
| 조문 적중 | **6/12** |
| 멀티턴 | 2/5 완전 통과 |

### 증명된 것

**세액은 전부 맞았습니다.** 다섯 계정이 각각 다른 계산 분기를 담당하는데
(분리과세 종결 / 비과세 제외 / 비교과세 ①<② / ①>② + Gross-up / Gross-up 대상 0),
전부 손계산 기대값과 일원 단위까지 일치했습니다.

| 계정 | 결정세액 | 선택 |
|---|---:|---|
| `antman` | 계산 미수행 (분리과세 종결) | — |
| `isabu` | 16,250,660 | ① |
| `jonber` | 3,559,890 | ② |
| `richman` | 66,274,240 | ① |
| `americano` | 13,877,520 | ① |

경계값도 지켰습니다. 정확히 2,000만원일 때 "이하는 분리과세"로 판정했습니다.

**소유자 격리는 한 장으로 설명됩니다.** 같은 질문(`저 종합과세 대상인가요?`)을
한 글자도 바꾸지 않고 다섯 계정에 던졌습니다. 다섯 응답이 **같은 근거를 같은 유사도 점수로**
인용하고, 도구가 돌려준 금액만 다릅니다. 그 차이가 그대로 판정을 가릅니다.

**거절은 거의 공짜였습니다.** 양도세·투자자문·타인 계좌·인젝션·장문 공격 등
17건이 주 모델을 한 번도 부르지 않았습니다.

## 4. 실패에서 확인된 것

### ① RAG 경로에 사실 검증 장치가 없습니다 — 가장 큰 구멍

`비영업대금 이익은 세율이 다른가요?`에 이렇게 답했습니다.

> "일반적인 이자소득과 동일하게 **원천징수세율 14%**가 적용됩니다. [출처: 소득세법 §16①]"

**정답은 25%입니다.** 법령 원문과 저희 문서 둘 다 25%로 적혀 있습니다.
이자 세율 조문(§129①1호) 대신 배당 세율 조문(§129①2호)이 회수됐고, 모델이 빈자리를
일반 지식으로 메운 뒤 §16①(이자소득의 *정의*)을 세율 출처인 것처럼 붙였습니다.

**출처가 붙어 있어서 오히려 더 믿음직해 보입니다.** 도구 경로라면 인용 충실도 검사에
걸렸겠지만, 규정 질문은 도구를 쓰지 않아 검사 대상이 아닙니다.
**설계가 덮지 못한 영역이 정확히 여기입니다.**

### ② 검색은 어휘가 겹칠 때만 작동합니다

`그로스업 비율이 몇 퍼센트인가요?`에는 "근거에서 확인되지 않습니다"라고 답했습니다.
그런데 답은 문서에 있습니다 — `## 배당가산율은 100분의 10이다`라는 청크가 통째로 있습니다.

원인은 **어휘 격차**입니다. 본문에 "그로스업"이라는 낱말이 한 번도 나오지 않습니다.
`Gross-up`은 문서 제목에만 있는데, 청크 텍스트에 제목이 포함되지 않습니다.

같은 문서를 **`배당세액공제`로 물으면 4/4 회수, `그로스업`으로 물으면 0/4**입니다.
질문 표현 하나로 성공과 실패가 갈립니다.

> 다만 **모델은 지어내지 않았습니다.** 근거가 없자 규칙대로 거절했습니다.
> 안전장치는 작동했고 실패한 것은 검색입니다. 두 실패는 구분해서 봐야 합니다.

### ③ 거절 규칙이 자기가 제시한 대안을 막습니다

```
턴2  "거기에 타사 배당 1,000만원 더하면요?"
     → 거절. "금액을 알려주시면 합산해 계산해 드리겠습니다"   ← 이미 알려주셨습니다
턴3  "그 금액이면 신고해야 하나요?"
     → 15,259,710원 그대로. 판정이 뒤집히지 않습니다
```

거절이 대화 상태 저장보다 **앞에서** 반환되어, 고객이 준 금액이 기억되지 않습니다.
시드는 합산하면 경계를 넘도록(25,259,710원) 설계했는데 그 장면이 나오지 않습니다.

**안내 문구와 코드가 어긋나 있습니다.** 대안 제시가 말뿐입니다.

### ④ 열거한 만큼만 막고, 열거한 만큼만 잡습니다

| 사례 | 통과한 표현 | 결과 |
|---|---|---|
| 투자자문 거절 | `팔면` · `손해` 미등록 | 모델 호출 836토큰 |
| 본인 지칭 인식 | `제 ISA **수익도**` (낱말 2개) | 도구 미호출, 일반론 답변 |
| 대명사 해소 | `그럼 저는요?` | "조회하겠습니다"라고만 하고 미조회 |

패턴 기반 방어의 한계입니다. **코드 방어도 열거에 의존하는 한 완전하지 않습니다.**

### ⑤ 만들어 둔 가드가 배선되지 않았습니다

총급여를 근로소득금액으로 오인하는 것은 실무에서 가장 흔한 오류입니다.
이를 잡으려고 `mentionsGrossPay()`를 만들었으나 **어디서도 호출되지 않는 데드 코드**였고,
해당 함정 질문에 되묻지 않고 넘어갔습니다. 테스트가 없으면 죽은 가드를 발견할 수 없습니다.

## 5. 실험 중 발견해 수정한 것

실험이 설계 결함을 세 건 드러냈고, 모두 코드로 고쳤습니다.

**계정 간 대화 유출.** `conversationId`를 고객이 보낸 값 그대로 써서, 하나의 방에
세 계정의 금융소득이 섞였습니다. 한 고객이 다른 고객의 배당금액을 인용한 답변을 받았고,
대화 조회 API에는 소유자 검증이 아예 없었습니다.
**도구 계층은 격리했는데 기억 계층이 우회하고 있었습니다.**
방 키를 `{계정}:{방}`으로 바꿔 남의 방을 가리킬 이름 자체를 만들 수 없게 했습니다.

**모르는 값을 0으로 놓고 계산했습니다.** 다른 종합소득을 묻지 않은 채 0원으로 계산해
"추가 납부하실 세액은 없습니다"라고 답했습니다. 근로소득이 있으면 완전히 틀린 답입니다.
"미상"과 "고객이 0이라고 답함"을 분리하고, **미상이면 계산하지 않고 되묻도록** 바꿨습니다.

**모델 등급이 인용 충실도를 좌우했습니다.** `gpt-4o-mini`는 근거를 다 받고도 고객 숫자 대신
법령 문장을 베꼈습니다. 프롬프트 강화로는 잡히지 않았고, 지시를 늘리자 오히려 악화됐습니다.
주 답변 모델만 `gpt-4o`로 올리고 라우터·폴백은 mini로 두었습니다.
**토큰 수는 동일(2,634)했고 차이는 단가뿐**이었습니다.

## 6. 한계와 다음

**우선순위가 높은 것**

1. 규정 경로의 사실 검증 — 세율·금액을 문서에서 파싱해 답변과 대조하는 축이 필요합니다
2. 거절과 상태 저장의 순서 — 금액이 포함된 문장은 거절 전에 기록해야 합니다
3. 검색 재현율 — 청크에 문서 제목을 포함하고, 문서 본문에 고객 용어를 함께 적습니다

**남은 한계**

세율·공제는 2026년 귀속 실습용 단순화이며 인적공제 상세는 다루지 않습니다.
자사 계좌와 마이데이터 연동 기관 외의 금융소득은 고객 진술에 의존합니다.
이 한계는 숨기지 않고 계산 전개에 표시합니다.
